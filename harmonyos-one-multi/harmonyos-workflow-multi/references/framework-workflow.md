# H5、Flutter、RN 接入五步流程

统一的是范围、批次、SPEC、确认、施工、验证与报告，不是工程结构或扫描方式。领域 Skill 提供诊断、修法和验收知识；其中“新适配”“问题定位”等方法拆到当前步骤使用，不在 SPEC 确认前执行修改。

## 第一步：识别范围并分批

先确认源码层、入口、主要页面或功能区、公共依赖和构建命令。足以确定修改边界及批次即可，不要求三方工程先枚举完整路由图，也不要求编写新的通用扫描器。

| 框架 | 分析入口与范围 | 领域知识 |
|---|---|---|
| ArkTS | 页面注册、导航与公共组件；工程范围使用 `project-scan.py`，明确局部范围可直接分析 | `harmonyos-ui-multi` / `harmonyos-camera-multi` |
| H5 | Web 入口、前端路由、页面组件、样式与尺寸计算；另核实 ArkTS Web 容器及加载关系 | `harmonyos-h5-multi`，先执行其输入边界审计 |
| RN | `package.json` 与锁定版本、应用入口、导航 Screen、公共布局；按需关联 RNOH 宿主及原生扩展 | `harmonyos-rn-multi`，先执行其输入边界审计 |
| Flutter | `pubspec.yaml` 与锁定依赖、`lib/` 入口、页面 Widget、导航与公共布局；按需关联 `ohos/` 宿主、插件 | `harmonyos-flutter-multi`，沿用已有 Flutter 或 HADSS 实现路线 |

### 源码分属不同工程

- H5 宿主与前端可在不同仓库，RN/Flutter 也可能分离宿主。记录已提供的源码根、实际关联和缺失端；加载 URL、离线包或压缩 bundle 不等于拿到了可维护源码。
- 双端纳入同一任务时，使用用户确认且可访问的共同工作目录作为任务根，在该目录维护一份 `.onemulti`；`task.scope` 只列本次仓库或子目录。所有页面和修改文件按任务根记相对路径，不移动业务源码，不分析共同目录中的其他工程。共同目录应尽量窄，不能为容纳分散仓库擅自提升到用户主目录；否则先确认工作区安排。
- 框架、各源码根、宿主关联、命令工作目录及缺失端写入已有 `decisions`，不新增一套状态文件。不满足访问条件时先说明缺口，不绕过工具权限。
- 只提供宿主时可以处理容器问题，但不能声称已经分析 H5/RN/Flutter 内部页面；依赖缺失端的问题保留交接，不虚构其代码或验证结果。

### 可选风险筛查

范围较大或需要筛选线索时，workflow 可对已确认源码目录运行：

```bash
node $OM/scripts/scanners/scan-h5-adaptation.mjs <H5源码目录>
node $OM/scripts/scanners/scan-rn-adaptation.mjs <RN源码目录>
```

每次只传一个目录；脚本不追踪远程 URL、不自动关联其他仓库。输出为风险文本，不是页面清单或已确认问题。退出码 `1` 表示高风险线索，不是执行失败；`0` 也不证明没有 UI 问题。Flutter 按工程源码和领域知识分析，不为统一形式强加扫描脚本。

页面/功能及公共依赖确认后建立批次，公共改动在依赖页面前处理，能独立验收的功能可分批。`pages` 使用真实页面或承载功能的源码文件，支持 `.vue/.tsx/.dart/.ets`，不把 URL 或路由名冒充文件路径。分析结果直接写入现有账本；多框架局部清单不能用 `merge-pages --full-scan` 覆盖其他已登记范围。

按 [路由表契约](route-map.md) 记录本次需要的访问路径，不追求全工程路由覆盖。已知目标文件但缺运行入口时用空 `steps` 与 `unavailableReason` 记录，不阻断源码侧五步交付，相关设备项记未验证；其他未知动态边记入 `unresolved`，不编造可执行步骤。

## 第二、三步：SPEC、高保真与施工

第二步按批加载对应领域知识，核实风险线索并分析未命中脚本规则的问题，再形成根因、方案、计划文件和验证项。输入不足的单端任务明确可完成部分及对端交接，不扩写成双端全部修复。

高保真遵循 [交付契约](hifi-delivery.md) 的批次与设备覆盖要求；视觉稿对应实际框架的实现，不把 H5/RN/Flutter 改写为 ArkUI。确认后第三步按计划实施，公共布局、桥接或插件改动保留原工程所有权与版本约束。

## 第四步：按工程实际链路验证

复用 [验证流程](verification.md) 的多模态探测、设备选择、五轮修复、证据关联及停止条件。H5 先按下节判断部署条件；SPEC 已明确验证计划且用户已确认继续时，不重复询问测试范围。新增范围、生产发布或安装新模拟器仍需单独确认。

### H5 部署判断

1. 核实工程的本地启动或部署方式，以及 WebView 加载地址。支持本地运行时启动或复用服务，再检查目标设备能否访问本轮修改后的资源；电脑与设备的 `127.0.0.1` 不能直接视为同一服务。
2. 需要开发者部署时询问：“本轮 H5 修改需要部署后才能进行设备验证。是否已完成部署？请提供或确认访问地址。”提供“已部署，继续验证”和“暂不部署，跳过设备验证”；未回复则等待，不代替用户选择跳过。
3. 确认已部署后仍须核实设备实际加载本轮资源，不能只凭服务启动或用户回复判定验证通过。未部署时不准备设备；用户选择暂不部署后，相关设备项记 `not_verified`，说明部署缺口。
4. 设备不可用不阻断已确认的浏览器检查。多模态探测通过且已有测试授权时，可完成计划内的浏览器交互与视觉检查；浏览器与 ArkWeb 设备结果分别登记，不相互替代。不因缺设备新增计划或自动下载镜像。

### RN 运行条件

构建前读取工程脚本，确认依赖安装、Codegen、bundle 和宿主构建的依赖顺序；需要 Codegen 时先按工程锁定命令生成所需文件，不手改生成物，也不要求每批重复生成。

准备设备前先确认兼容宿主及本轮 bundle 的加载方式：已有可用宿主时复用；没有可用宿主或宿主/原生扩展变更时先构建宿主，不要求每批重建。设备连接后仍须核实实际加载本轮资源，bundle 成功不代表宿主可运行。

宿主构建失败时，属于本批且范围内可修复的问题继续修复重测；SDK、工具链等环境问题记录后交开发者处理，超出范围的环境变更另获授权。无法继续时设备项记为未验证，不持续准备设备，也不取消后续可修复问题的重测。

### 构建与运行

| 对象 | 基础检查 | 运行验证 |
|---|---|---|
| H5 | 在前端根执行工程已有构建、类型/样式检查；修改宿主时另外构建宿主 | 确认 WebView 实际加载本轮修改的资源，进入目标 H5 页面，不以宿主启动代替页面验证 |
| RN | 按锁定工具链检查 JS/TS、生成 bundle；宿主构建与复用按上节判断 | 确认本轮 bundle 和宿主配套，验证实际 Screen 的尺寸、交互和状态 |
| Flutter | 按工程已有 Flutter 工具链执行分析、相关测试及目标构建；宿主/插件变更需要重装 | 确认运行的是本轮 Dart 与宿主产物，验证实际 Widget 页面及形态切换 |

- 命令来自工程脚本、锁定工具链和领域知识，不统一写死 `npm`、`flutter build` 或 `devecocli build`；使用各自正确的工作目录。第一步执行同样适用的命令记录修改前基线。
- `run-foundation.py` 的默认构建、检查和装机入口用于原生 ArkTS。三方流程由 Agent 执行已确定命令，并用 `evidence-session.py record-batch` 登记真实 `argv/exitCode/links`；`cwd` 为任务根相对工作目录。构建命令标记 `phase=framework_build`，适用静态检查标记 `phase=framework_check`。每轮一次登记本批完整的适用基础检查集，报告聚合该轮结果，不能只登记最后成功的宿主构建。风险扫描只作诊断线索，不直接算基础检查通过或失败。
- 适用的宿主 `deviceTypes` 检查在宿主根运行；原生 `.ets` 静态检查不能证明 CSS、TSX 或 Dart 已验证。没有适用检查时说明，不制造成功命令。
- 只有包源码且没有可执行目标构建时，照常记录已完成的分析/测试，基础构建保留未验证；不把 `analyze/test` 伪装成 `framework_build`。
- H5 需要部署、RN 需要启动打包服务时先核实工程现有方式；生产发布或超出任务范围的环境变更需另获授权。仅浏览器预览不能替代 HarmonyOS WebView 目标形态验证；未加载本轮资源或缺少可运行宿主时，相关项记为未验证。
- 路径动作由当前环境实际可用的工具执行。原生组件树可能只有 WebView/Surface 外壳，不能据此证明内部元素正确；图片不能判断且无适用 DOM、语义树或节点工具时，记录证据不足，不伪造定位器。仍遵守多模态失败分支，不用组件树绕过授权或模型能力探测。
- 浏览器检查命令使用 `phase=browser_regression`，设备检查使用 `phase=device_verification`；相应环境检查可使用 `browser_preparation/device_preparation`。只登记实际执行的命令，`links` 精确关联计划项；报告据此区分执行环境，不凭设备形态或检查项名称猜测。

## 第五步：统一报告

继续使用同一 `decisions.json`、`evidence/index.json` 和 HTML 报告命令。区分前端、宿主和缺失端的覆盖范围，构建通过不代表设备效果已验证；每批出报告，全部批次终态后出汇总。
